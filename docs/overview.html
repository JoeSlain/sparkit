Sparkit

Un template MIT prêt à cloner : app mobile native (iOS/Android), app web SPA, et un vrai backend Supabase local — avec auth, profil et tâches privées en FR/EN.

Ce qu’on a aujourd’hui

Deux apps Web (React + Vite + React Router) et mobile (Expo + Tamagui), sans Expo Web.
Données réelles Supabase Auth + Postgres + Storage, schéma Drizzle, RLS testée.
Exemple métier Inscription / connexion, profil, CRUD tâches privées, cache par utilisateur.
Outillage pnpm, Lingui FR/EN (+ i18n:translate IA optionnel), générateur, verify, CI écrite (non publiée).

Dépôt local sur main (commits bee42c8 + docs). Pas de remote GitHub, pas d’EAS cloud, pas de stores.

À quoi ressemble le travail au quotidien

1
Installer et démarrer la stack

pnpm install --frozen-lockfile → pnpm db:start → pnpm db:seed. Comptes démo locaux : alice / bob (@example.test).

2
Développer le web

pnpm dev:web sur http://127.0.0.1:5173. Même logique métier que le mobile, UI web séparée.

3
Développer le mobile

Depuis apps/mobile : stim start puis stim ios ou stim android (une plateforme à la fois). Fast Refresh pour le JS.

4
Valider

pnpm verify (format, lint, types, tests, builds). Après extract : pnpm i18n:translate si une clé IA est dispo, puis check/compile. Backend : pnpm db:test. Web E2E : Playwright. Natif : Stim + Argent / Maestro.

5
Créer un produit à partir du template

pnpm create:project ../mon-app --name mon-app --targets both (ou web / mobile). Nouveau repo, nouveau lockfile, pas de secrets copiés.

Mental model

  • Tu changes le produit (écrans, schéma, messages), pas un framework magique.
  • Les packages partagent contrats / validation / i18n / client Supabase — pas les composants UI.
  • Les services payants (Sentry, PostHog, RevenueCat…) sont des recettes documentées, pas branchés.

État de validation (honnête)

OK Install figé, pnpm verify, Vitest / Jest, builds web + Hermes, backend (pgTAP + intégration), Playwright 3/3, Stim iOS sim + Auth, Stim Android sur Pixel 9 Pro (build/launch).
Partiel Maestro : arrive à l’auth, sign-in flaky (focus TextInput / clavier). Générateur : copies QA validées, pas un verify exhaustif sur chaque variante. Worktree live : pas encore rejoué de bout en bout.
Absent Remote GitHub, CI exécutée en ligne, EAS / OTA cloud, comptes SaaS branchés, soumission stores, parcours Maestro 100 % vert.

Ce qu’il manque (si tu veux “produit publié”)

  • Décider d’un remote + push (aujourd’hui tout est local).
  • Stabiliser Maestro (ou un flow Argent) pour le parcours auth → tâches sur device.
  • Brancher seulement les profils optionnels dont tu as vraiment besoin.
  • Configurer EAS / identifiants stores / redirects Auth de prod quand tu es prêt à ship.
  • Garder ~10–15 Gio libres pour AVD Android ; sur téléphone : URL LAN Supabase, pas 10.0.2.2.

Pour un usage “starter interne / base de projet”, tu as déjà le cœur : code, preuves locales, générateur, docs.
