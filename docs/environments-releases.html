Environnements & chemin vers la prod

Overview pour sparkit : comment organiser local → staging → production, branches Git, builds natives, OTA, web, migrations Supabase, et données de test — sans mélanger les secrets ni la prod.

1. Les 3 environnements (modèle retenu)

Local Laptop + Docker. Stack Supabase du checkout (pnpm db:start). Worktrees = stacks isolées. Données seed / fixtures.
Staging Projet Supabase séparé + web staging + builds mobiles sur channel preview / TestFlight / Play internal. Données synthétiques.
Production Projet Supabase prod + web prod + store builds channel production. Secrets GitHub Environments + review obligatoire.

Règle d’or : 1 environnement = 1 projet Supabase + 1 set de secrets + 1 URL app. Jamais la clé service-role ou les données clients dans un build mobile / web public.

Varlock sert à valider les variables (types, présence) avant run — pas à remplacer les secrets cloud (EAS / GitHub Environments / Varlock remote si on l’active plus tard).

2. Comment le code bouge (pipeline)

Dev
Branche courte feat/… → PR → CI (verify, tests). Web preview optionnel. Mobile : Stim local ou EAS Update sur channel de feature si besoin.
Merge main
Trunk toujours “shippable”. Feature flags pour le travail incomplet. Pas de long develop à la GitFlow (sauf si on force un dual-trunk plus tard).
Staging
Migrations supabase db push vers projet staging. Deploy web staging. OTA / build interne → channel preview. Smoke E2E + RLS avec comptes seed.
Prod
Promote après soak staging : migrations prod (review GitHub Environment), web prod, puis soit OTA production (JS only), soit nouveau binaire store (natif changé).

Branches Git (recommandation pour ce monorepo)

  • GitHub Flow : main + PRs courtes. Adapté monorepo web + mobile (éviter GitFlow lourd).
  • Stores : quand on soumet une version, cut optionnelle release/x.y.z depuis main pour stabiliser / hotfixes cherry-pick — pattern M&S / release-train, sans ramener un develop permanent.
  • Tags vX.Y.Z après publication store (ou après deploy web si web-only).

3. Deux chemins de release : web vs mobile

Couche Qu’est-ce qui change Comment shipper
Web SPA JS/CSS/assets Build Vite → hébergeur (preview PR → staging → prod). Rollback = redeploy commit précédent.
Mobile JS Bundle JS/assets compatibles OTA EAS Update sur channel. Prérequis : même runtimeVersion que le binaire.
Mobile natif SDK, plugins, entitlements, native deps Nouveau EAS Build → TestFlight / Play → review stores. OTA impossible pour ces changements.
Backend Migrations Drizzle → SQL Supabase, RLS, Storage CI db push staging puis prod. App et schéma versionnés ensemble ; compatibilité forward si possible.

OTA / channels / bundles (déjà amorcé dans le template)

  • eas.json : profiles development, preview (channel preview), production (channel production).
  • runtimeVersion.policy: fingerprint dans app.json — le runtime suit la surface native (sécurité forte). Expo blog 2026 recommande souvent appVersion + fingerprint en gate CI ; les deux sont valides : fingerprint-as-policy = rebuild dès que le native change (plus de builds, moins de mauvaises OTA).
  • Process Expo “simple” : publier sur preview / staging → tester → eas update:republish vers production (même bundle testé). Rollouts % + rollback documentés.
  • Avant OTA : eas fingerprint:compare vs build prod. Si diff → build store, pas update.

4. Données : staging ≠ copie de prod

  • Par défaut : seed synthétique (alice/bob locaux, fixtures CI). Pas d’export prod “pour que ce soit réaliste”.
  • Si un jour on a besoin de réalisme : subset anonymisé (PII, tokens, paiements, fichiers privés retirés) + procédure écrite + accès restreint. Jamais dans le repo.
  • Tester RLS avec deux users seed via l’API (pas seulement le SQL editor, qui bypass RLS).
  • Auth redirects, OAuth, webhooks, emails : configs propres à l’env (test keys staging).
  • Supabase Branching (preview DB par PR) = option plus tard ; pour démarrer, 2 projets cloud (staging + prod) + local suffisent.

5. Secrets & config par environnement

Où Quoi
Local .env* gitignored, générés par pnpm db:start / env:local. Varlock valide le schéma.
CI GitHub Environments staging / production (reviewers sur prod). Secrets projet Supabase séparés.
EAS Env vars par profile (development / preview / production) : URL + publishable key du bon projet Supabase.
Clients Uniquement URL + clé publique (RLS). Service role = serveur / jobs CI seulement.

6. Matrice “aujourd’hui vs à brancher”

Sujet État template
Varlock + .env.schema Présent
Local Supabase + seeds + pgTAP / intégration Présent
EAS profiles / channels / fingerprint Config écrite, pas de projet EAS cloud
CI GitHub Workflows écrits, remote pas publié
Projets Supabase staging/prod + deploy migrations À créer au moment release
Hébergement web staging/prod Recette docs, pas branché
OTA réelle + rollouts + rollback runbook Après connexion EAS
Feature flags / canary prod Optionnel (PostHog etc.)

Décision pratique pour “nous”

  1. Rester sur GitHub Flow + main shippable.
  2. Créer 2 projets Supabase (staging, prod) quand on publie le remote ; migrations via CI, jamais laptop → prod.
  3. Web : preview PR → staging → prod. Mobile : build preview pour tester OTA ; build production store ; OTA seulement si fingerprint OK.
  4. Données staging = seed / anonymisé. Jamais prod dump par défaut.
  5. Promote OTA avec republish du bundle déjà validé staging ; garder la commande de rollback collée dans le canal release.
  6. Varlock reste le garde-fou local/CI des variables ; les secrets live vivent dans GitHub / EAS.

Ce n’est pas une autorisation de créer des comptes cloud ni de soumettre aux stores — c’est le plan d’organisation une fois qu’on décide de shipper.
